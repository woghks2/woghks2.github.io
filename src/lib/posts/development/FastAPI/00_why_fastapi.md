# 0. 왜 FastAPI인가?

새로운 백엔드 프로젝트를 시작하거나 아키텍처를 설계할 때, 다들 **"이번엔 어떤 프레임워크를 쓰지?"** 라는 고민 한 번쯤 해보셨을 겁니다. Spring Boot, Django부터 Next.js, Rails와 같은 풀스택 프레임 워크도 있습니다. 

* **Java/Kotlin 진영의 굳건한 대표 주자**: **Spring Boot**
* **JavaScript/TypeScript 진영의 확장성**: **Node.js (NestJS, Express)**
* **Python 진영의 현대적 대안**: **FastAPI**

과거의 Python 개발은 Django나 Flask를 사용했습니다. 하지만 현대의 비동기 마이크로서비스나 API 중심의 환경으로 넘어오면서, 이제는 **FastAPI가 대세**로 자리 잡았습니다.

이번 글에서는 간단한 비교를 통해서 살펴보겠습니다.

---

## 1. 백엔드 프레임워크 요약 비교

각 진영의 프레임워크들은 지향하는 철학과 기술적 강점이 뚜렷하게 나뉩니다.

| 항목 | Spring Boot (Java/Kotlin) | Node.js (TypeScript/NestJS) | FastAPI (Python) |
| :--- | :--- | :--- | :--- |
| **타입 안전성** | 매우 강력함 <br>(정적 컴파일 타임) | 강력함 <br>(컴파일 타임 / 인터프리터 런타임) | 강력함 <br>(Pydantic 런타임 검증 및 타입 힌트) |
| **비동기 처리** | 가상 스레드(Virtual Thread) 도입으로 대폭 강화 | 싱글 스레드 이벤트 루프 기반으로 매우 뛰어남 | Python Asyncio 및 ASGI 아키텍처 기반으로 뛰어남 |
| **개발 생산성** | 무겁고 초기 보일러플레이트 코드가 많음 | 빠르고 풍부한 패키지 생태계 활용 가능 | 극도로 빠름 <br>(자동 문서화 및 직관적 데코레이터) |
| **주요 생태계** | 엔터프라이즈, 금융, 대기업 | 풀스택 웹 애플리케이션, 실시간 채팅, 서버리스 | AI/ML 연동, 빠른 데이터 API, MSA 마이크로서비스 |

FastAPI는 **Node.js 급의 가벼운 비동기 성능**, **Spring Boot 못지않은 타입 검증의 안전성**, 그리고 **Python이 가진 강력한 AI/ML 생태계**를 한곳에 녹여낸 프레임워크라고 볼 수 있습니다.

---

## 2. Python에서 FastAPI

파이썬 환경에는 이미 쟁쟁한 대형 프레임워크들이 존재함에도 불구하고, 많은 신규 프로젝트에서 FastAPI를 사용하고 있습니다.

### 2.1 Django의 무거움 탈피와 패러다임의 변화

**Django**는 로그인, 관리자(Admin) 페이지, 자체 ORM, 템플릿 엔진 등 웹 개발에 필요한 거의 모든 도구가 내장되어 있어 풀스택 애플리케이션을 빠르게 만들기에는 최적의 선택지입니다.

그러나 프론트엔드와 백엔드가 명확히 분리된 현대의 SPA 환경이나 MSA 아키텍처에서는 Django의 이러한 비대함이 오히려 무거운 병목이 되곤 합니다.

* **동기식 WSGI의 한계**: Django는 태생이 동기식 WSGI 표준 위에 빌드되어 있어 비동기(Async) 처리를 유연하게 다루기 어렵습니다. 최근 버전에서 비동기 기능이 추가되고 있으나, 생태계 내부의 많은 라이브러리(대표적으로 ORM)가 여전히 동기식 블로킹 방식으로 동작합니다.
* **API 개발의 번잡함**: REST API를 만들기 위해 Django REST Framework(DRF)를 추가로 얹어야 하는데, Serializer 설정 및 뷰셋 구성 과정에서 작성해야 하는 보일러플레이트 코드가 많고 무겁습니다. (사실 보일러 플레이트가 많아도 AI가 잘 쳐주기 떄문에 나쁘지 않을지도...)

| 비교 항목 | Django (+ DRF) | FastAPI |
| :--- | :--- | :--- |
| **아키텍처 모델** | 모놀리식 (풀스택 지향, Batteries-included) | 마이크로 프레임워크 (API-first, Lightweight) |
| **기본 실행 환경** | WSGI (동기식 디폴트) | ASGI (비동기 Async 네이티브) |
| **데이터 검증** | DRF Serializer | Pydantic (타입 힌트 기반) |
| **API 문서화** | Swagger 설정을 위해 추가 패키지 필요 | 내장 기능으로 코드 작성 즉시 자동화 (`/docs`) |
| **주요 활용처** | 관리자 페이지가 필수적인 풀스택 대형 웹 서비스 | 고성능 머신러닝 API, 실시간 비동기 API, MSA 서버 |


### 2.2 Flask의 보일러플레이트 해결

Flask는 매우 가볍다는 장점이 있지만, 프로젝트가 조금만 커져도 데이터 검증, 데이터베이스 조립, 직렬화, OpenAPI 문서화 등을 개발자가 일일이 수동으로 라이브러리를 찾아 설정해야 합니다. 이로 인해 개발자마다 코드 구조가 천차만별로 바뀌어 오히려 유지보수가 어려워진다는 단점이 있습니다.

### 2.3 FastAPI의 장점

FastAPI는 Django의 풍부한 기능과 Flask의 미니멀리즘 사이에서 **개발자에게 가장 필요한 본질**만 영리하게 챙겼습니다.

* **Pydantic 기반의 자동 타입 검증**: Python의 타입 힌트(Type Hint) 하나만 적어주면 알아서 들어오는 모든 요청의 유효성을 검사합니다. 잘못된 데이터가 들어오면 구구절절 예외 처리할 필요 없이, 알아서 `HTTP 422` 에러를 발생시켜줍니다.
* **대화형 OpenAPI 문서 자동 생성**: 코드를 짜기만 하면 별도의 설정 없이도 `/docs` (Swagger UI) 문서가 실시간으로 만들어집니다.
* **네이티브 비동기(ASGI) 지원**: 과거 WSGI 기반의 전통적인 Python 프레임워크들과 달리, FastAPI는 비동기 ASGI 서버(Uvicorn) 위에서 작동합니다. `async/await` 문법을 사용해 비동기 I/O를 처리합니다.

## 3. 비동기 백엔드

FastAPI의 성능을 논할 때 가장 많이 언급되는 단어는 단연 **'비동기'**입니다. 비동기 백엔드의 진정한 장점은 대기 시간의 효율적인 재사용에 있습니다.

대부분의 웹 애플리케이션에서 발생하는 병목 지점은 서버 내부의 CPU 연산이 아니라, 외부 자원을 대기하는 시간(**I/O Bound**)입니다.

* 데이터베이스(SQL/NoSQL) 조회 대기 시간
* 외부 타사 API(결제 모듈, 알림 서비스 등) 호출 대기 시간
* 파일 시스템 및 스토리지 입출력 대기 시간

전통적인 동기식 백엔드는 하나의 요청을 처리하는 동안 스레드가 I/O 대기 시간에 묶여서 멈춰 있습니다. 반면 FastAPI의 비동기 이벤트 루프는 외부 응답을 기다리는 동안, 해당 스레드를 즉시 다른 클라이언트의 요청을 처리하는 데 활용합니다. 덕분에 훨씬 적은 양의 메모리와 스레드 리소스만으로 수배에서 수십 배 더 많은 동시 요청을 감당할 수 있습니다.

---

## 4. 아키텍처 관점에서의 FastAPI 장점

웹 서비스를 장기적으로 안정적으로 운영하려면 아키텍처 관점에서의 유지보수성이 핵심입니다. FastAPI는 이를 위해 다음과 같은 유연함을 제공합니다.

### 4.1 의존성 주입(Depends) 기반의 유연성

FastAPI 내부의 `Depends` 시스템은 엔드포인트가 특정 모듈에 종속되지 않도록 돕는 훌륭한 IoC(제어의 역전) 엔진입니다. 이 DI(Dependency Injection) 덕분에 비즈니스 도메인 코드와 데이터베이스 저장소 코드를 깔끔하게 격리하여, 테스트 가능한 유연한 레이어드 아키텍처를 손쉽게 구축할 수 있습니다.

### 4.2 빠른 목업에서 프로덕션 전환

처음에는 파일 한두 개에 간단한 파이썬 함수랑 Pydantic 모델 몇 개만 얹어서 빠르게 프로토타입 API를 완성할 수 있습니다. 

보통 이렇게 대충 만들면 나중에 서비스가 커졌을 때 코드를 통째로 갈아엎어야 하는데요. FastAPI는 이 구조를 그대로 유지하면서, DI를 활용해 점진적으로 확장할 수 있습니다. 

---

## 5. FastAPI가 필요한 경우

* **기존에 Python으로 작성된 머신러닝/AI 모델**을 빠르게 웹 API 서비스로 래핑하여 배포해야 할 때
* 대용량 대기 시간이 빈번하게 발생하는 MSA를 설계할 때
* 개발 인력이 적고 일정이 촉박하여 **빠른 속도의 API 개발과 즉각적인 스펙 문서화**가 필요할 때
* 프론트엔드 협업 시 API 문서가 수시로 바뀌어 **실시간으로 동기화되는 인터페이스 스펙 문서**가 필요할 때 (사실 다른 프레임워크도 쉽게 구현 가능하다.)

이전에 FastAPI로 프로젝트를 진행한 경험도 있고, 회원 관리가 없는 서비스다 보니 FastAPI를 선택해서 프로젝트를 진행을 하는데,추후에 VectorDB나 ML/AI 모델 확장을 생각해서 파이썬 계열을 선택했습니다.
