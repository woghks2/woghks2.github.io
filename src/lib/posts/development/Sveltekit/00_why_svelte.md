# 0. 왜 Svelte인가?

프로젝트를 시작할 때 가장 먼저 마주하는 질문은 대개 비슷합니다.

**"이번에는 어떤 프런트엔드 프레임워크를 쓸 것인가?"**

**React**가 가장 넓은 생태계를 가지고 있고, **Vue**도 낮은 진입 장벽과 안정적인 프레임워크 경험을 제공합니다. 그 사이에서 **Svelte**는 다른 방향을 택합니다. 브라우저 런타임에서 많은 일을 처리하기보다, 빌드 시점에 가능한 일을 최대한 컴파일해 두는 방식입니다.

Svelte 5는 여기에 **Runes(룬)**라는 명시적 반응성 모델을 도입했습니다. 이번 글에서는 Svelte 5가 React/Vue와 어떤 지점에서 다른지, 그리고 어떤 프로젝트에서 고려할 만한 선택지인지 정리해 보겠습니다.

---

## 1. 프런트엔드 프레임워크 요약 비교

각 프런트엔드 라이브러리들은 화면을 그리는 렌더링 방식과 상태 변화를 감지하는 아키텍처에서 뚜렷한 차이를 보입니다.

| 비교 항목 | React | Vue 3 | Svelte 5 |
| :--- | :--- | :--- | :--- |
| **반응성 구현** | 단방향 데이터 흐름 및 가상 DOM 갱신 | 프록시(Proxy) 기반 반응성 및 가상 DOM | 컴파일 타임 코드 생성 및 네이티브 DOM 제어 |
| **가상 DOM 사용 여부** | **사용함 (Virtual DOM)** | **사용함 (Virtual DOM)** | **사용하지 않음 (No Virtual DOM)** |
| **반응성 문법** | `useState`, `useEffect` 등 (수동 의존성 관리) | Composition API (`ref`, `reactive`) | **Runes** (`$state`, `$derived`, `$effect`) |
| **런타임 크기** | 비교적 큼 (React DOM 및 런타임 포함) | 중간 (반응성 런타임 포함) | 작음 (컴파일 결과 중심) |
| **개발 생산성** | 생태계가 넓지만 훅과 렌더링 최적화 규칙을 이해해야 함 | 템플릿과 Composition API의 균형이 좋음 | 상태와 마크업을 간결하게 연결하기 쉬움 |

> [!NOTE]
> **Svelte는 컴파일러 성격이 강한 프레임워크입니다**
> React나 Vue가 브라우저 런타임에서 프레임워크 엔진을 중심으로 화면 갱신을 조율한다면, Svelte는 빌드 시점에 컴포넌트를 분석해 필요한 DOM 갱신 코드로 변환합니다. 이 차이 때문에 런타임에 들고 가야 하는 코드와 갱신 절차가 상대적으로 줄어듭니다.

---

## 2. 가상 DOM을 사용하지 않는다는 것

React와 Vue는 화면을 빠르게 갱신하기 위해 실제 DOM과 똑같이 닮은 메모리 내 복사본인 **가상 DOM(Virtual DOM)**을 사용합니다. 상태가 변하면 가상 DOM 트리 전체를 새로 그리고, 이전 트리와 비교(Diffing)하여 바뀐 노드만 실제 브라우저 DOM에 적용하는 방식입니다.

과거에는 이 방식이 직접 DOM 조작보다 안전하고 빠른 기본 전략으로 받아들여졌습니다. 하지만 모든 화면 갱신에 가상 DOM 트리 생성과 비교 과정이 필요한 것은 아닙니다. Svelte는 이 작업을 런타임이 아니라 컴파일 단계에서 최대한 줄이는 쪽을 선택합니다.

### Svelte의 무(No) 가상 DOM 작동 방식

Svelte는 빌드 시점에 템플릿 코드(`{#if}`, `{#each}`)를 분석하여 어떤 변수가 변할 때 DOM의 어떤 노드를 갱신해야 하는지 미리 계산해 둡니다.

```javascript
// Svelte 컴파일 결과의 가상 코드 예시
// 가상 DOM 트리 비교 과정 없이 변수가 변하면 타깃 DOM 요소의 textContent를 다이렉트로 수정
if (changed.count) {
    div.textContent = count;
}
```

이 덕분에 Svelte는 브라우저 런타임에서 가상 DOM 트리를 만들고 비교하는 단계를 줄일 수 있습니다. 특히 반복 렌더링이 많거나 번들 크기에 민감한 화면에서는 이 구조가 장점으로 작동합니다.

---

## 3. 코드의 간결성: React vs Svelte

두 라이브러리로 작성된 단순한 '카운터' 예제 코드를 비교해보면 코드의 밀도 차이가 즉각적으로 드러납니다.

### React 코드
```jsx
import React, { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}
```

### Svelte 5 코드
```svelte
<script>
  let count = $state(0);
</script>

<button onclick={() => count++}>
  Clicked {count} times
</button>
```

* React는 상태를 바꾸기 위해 전용 세터 함수(`setCount`)를 사용하고, 상태 변경에 따라 컴포넌트 함수가 다시 실행됩니다. 이 모델은 명확하지만 렌더링 비용과 의존성 관리를 개발자가 함께 신경 써야 합니다.
* Svelte는 `$state`로 선언한 상태를 일반 변수처럼 다룰 수 있습니다. `count++`처럼 값을 바꾸면 이 값을 참조하는 화면 조각만 갱신됩니다.

---

## 4. Svelte 5와 Runes

Svelte 5의 **Runes(룬)**는 "이 값은 반응성 상태다", "이 값은 파생 상태다", "이 코드는 상태 변화에 반응해야 한다"는 의도를 코드에 명시하는 문법입니다.

```svelte
<script>
  // 1. 단순 상태 정의
  let count = $state(0);
  
  // 2. 파생(계산된) 상태 정의
  let double = $derived(count * 2);
  
  // 3. 부수 효과(Effect) 처리
  $effect(() => {
    console.log(`현재 카운트는 ${count}입니다.`);
  });
</script>
```

Runes의 도입으로 Svelte는 컴포넌트 내부에 묶여 있던 반응성 로직을 일반 `.svelte.js` 또는 `.svelte.ts` 파일로 옮기기 쉬워졌습니다. 상태 관리와 비즈니스 로직을 컴포넌트 바깥으로 분리하기 좋아졌다는 점이 Svelte 5의 핵심 변화입니다.

---

## 5. Svelte 5가 잘 맞는 경우

* **작은 팀에서 빠르게 화면을 만들어야 할 때**: 상태 선언, 이벤트 처리, 스타일 스코핑이 한 파일 안에서 단순하게 이어집니다.
* **번들 크기와 초기 로딩 속도가 중요한 서비스**: 컴파일 결과 중심의 구조 덕분에 런타임 부담을 줄이기 쉽습니다.
* **대시보드나 인터랙티브 UI처럼 잦은 화면 갱신이 있는 경우**: 필요한 DOM 조각만 직접 갱신하는 방식이 유리하게 작동할 수 있습니다.
* **SvelteKit까지 함께 사용할 경우**: 라우팅, SSR, 데이터 로딩, 폼 액션, 배포 어댑터까지 공식 프레임워크 안에서 일관되게 다룰 수 있습니다.

다만 Svelte는 React만큼 채용 시장과 서드파티 생태계가 넓지는 않습니다. 대규모 팀 표준화, 사내 컴포넌트 라이브러리, 외부 패키지 호환성이 중요한 조직이라면 이 부분을 함께 고려해야 합니다.

결국 Svelte 5는 "가장 인기 있는 선택지"라기보다, **작은 런타임, 명시적인 반응성, 빠른 UI 개발 경험**을 우선순위에 두는 프로젝트에서 강점을 발휘하는 선택지라고 볼 수 있습니다.
