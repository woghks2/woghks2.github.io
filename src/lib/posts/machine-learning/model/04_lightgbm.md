# 04. LightGBM (Light Gradient Boosting Machine)

앞서 살펴본 **XGBoost**는 2차 테일러 전개와 엄밀한 정규화(L2 규제, 사후 가지치기)를 통해 모델의 예측력과 안정성을 극대화했습니다. 하지만 대용량 데이터(수백만 행, 수백 개 특성) 앞에서는 모든 샘플을 정렬하고 전수 조사하느라 계산량과 메모리 소모가 크다는 한계가 있었습니다.

**LightGBM**은 이 연산 병목을 해결하기 위해 마이크로소프트에서 공개한 알고리즘입니다. "정확도는 거의 그대로 유지하면서, 연산 속도를 10배 이상 끌어올리고 메모리를 획기적으로 줄인다"는 목표 아래 개발되었으며, 핵심 아이디어는 데이터 압축 기법 3가지(Histogram, GOSS, EFB)와 새로운 트리 성장(Leaf-wise)로 요약됩니다.

---

## 1. 히스토그램 기반 분할 (Histogram-based Splitting)

전통적인 결정 트리나 초기 부스팅 모델은 모든 데이터 포인트를 정렬(Sort)한 뒤 가능한 모든 분할점을 일일이 검사했기 때문에, 데이터가 많아질수록 연산량이 폭발했습니다.

LightGBM은 연속형 특성값을 256개 정도의 고정된 구간(Bin)으로 이산화(Discretization)하여 처리합니다.

- 데이터를 정렬할 필요 없이, 각 구간별로 데이터 통계(Gradient의 합 $G$, Hessian의 합 $H$)를 담은 **히스토그램**을 구성합니다.
- 분할점을 찾을 때 데이터 전체 수($N$)를 순회하는 대신, Bin의 개수($K \approx 255$)\만 순회하면 되므로 분할 탐색 시간복잡도가 $O(N \times \text{Feature})$에서 $O(K \times \text{Feature})$로 대폭 줄어듭니다.
- 메모리 사용량도 실수형(Float 32bit/64bit) 대신 8bit 정수로 압축(Quantization)되어 1/8 수준으로 획기적으로 절약됩니다.

## 2. GOSS (Gradient-based One-Side Sampling)

> **"행(Row)을 줄이자: 이미 잘 맞힌 데이터는 덜 보고, 많이 틀린 데이터에 집중한다"**

부스팅에서 Gradient(오차)가 큰 샘플은 아직 학습이 덜 된 중요한 데이터지만, Gradient가 작은 샘플은 이미 정답에 가까워 배울 것이 적습니다. 그렇다고 오차가 작은 샘플을 무작정 버리면 원래 데이터의 분포가 왜곡됩니다. GOSS는 이를 해결하기 위해 **한쪽(One-side)만 샘플링**하는 기법을 씁니다.

1. **상위 추출**: Gradient 절댓값이 큰 **상위 $a \times 100\%$ 데이터는 100% 보존**합니다.
2. **하위 샘플링**: Gradient가 작은 나머지 데이터군에서 **$b \times 100\%$만 무작위(Random)로 추출**합니다.
3. **분포 보정 (가중치 증폭)**: 덜 뽑힌 작은 Gradient 샘플들에 가중치 $\frac{1-a}{b}$를 곱해 원래 데이터 크기의 영향력을 복원합니다.

$$\tilde{V}_j(d) = \frac{1}{n}\left( \frac{\left(\sum_{x_i \in A_l} g_i + \frac{1-a}{b}\sum_{x_i \in B_l} g_i\right)^2}{n_l^j(d)} + \frac{\left(\sum_{x_i \in A_r} g_i + \frac{1-a}{b}\sum_{x_i \in B_r} g_i\right)^2}{n_r^j(d)} \right)$$

수학적으로 데이터 크기 $n$이 충분히 크다면, 이렇게 계산한 분산 이득(Variance Gain)은 전체 데이터를 다 썼을 때의 오차와 거의 차이가 없습니다. 즉, **데이터의 10~20%만 보면서도 전체 데이터를 학습한 것과 대등한 효과**를 냅니다.

## 3. EFB (Exclusive Feature Bundling)

> **"열(Column)을 줄이자: 같이 쓰이지 않는 희소 변수들을 하나로 합친다"**

고차원 정형 데이터는 원-핫 인코딩(One-Hot Encoding) 등으로 인해 대부분의 값이 0인 희소(Sparse)한 상태가 많습니다. LightGBM은 **동시에 0이 아닌 값을 가질 일이 거의 없는 상호 배타적 특성(Mutually Exclusive Features)들을 하나의 특성으로 묶어버립니다(Bundle).**

### 오프셋(Offset)을 통한 고유성 보존
단순히 값을 더하면 원래 어떤 변수의 값이었는지 충돌(Collision)이 발생합니다. EFB는 값의 범위를 밀어내는 오프셋(Offset)을 사용해 이를 방지합니다.

1. **사전 Bin 변환**: LightGBM은 모든 피처를 사전에 0번부터 시작하는 히스토그램 바구니(Bin) 번호로 변환해 둡니다.
2. **최댓값 기반 오프셋 이동**: 피처 A가 `0~10`번 Bin을 쓴다면, 피처 B의 Bin 번호에는 피처 A의 최댓값(10)을 더해 `11~30`번 대역으로 번호를 뒤로 밀어버립니다.
3. **자연스러운 피처 식별**: 모델 입장에서는 별도 라벨 없이 번들 값이 10 이하이면 피처 A, 10을 초과하면 피처 B로 바구니 번호 대역만 보고 두 피처를 완벽히 구분해 분할할 수 있습니다.

* 특성 A의 범위: $[0, 10]$
* 특성 B의 범위: $[0, 20]$
* 변환: 특성 B의 값에 10(오프셋)을 더해 범위를 $[10, 30]$으로 변환한 뒤 하나의 단일 컬럼으로 합칩니다.
* 결과: 하나의 합쳐진 특성 값만 보고도 원래 특성 A의 값인지 B의 값인지 100% 복원할 수 있습니다.

완벽하게 배타적이지 않더라도 사소한 충돌은 약간 허용하며 탐욕적(Greedy)으로 묶어내므로, **모델이 탐색해야 할 피처 차원 수 자체를 획기적으로 압축**합니다.

## 4. Leaf-wise (리프 중심 성장): 빠른 수렴과 과적합의 양날의 검

기존 트리 모델(XGBoost 기본형 포함)은 트리의 좌우 균형을 맞추며 층(Depth) 단위로 넓혀가는 **Level-wise(수평 성장)** 방식을 사용했습니다. 반면 LightGBM은 트리의 균형을 고려하지 않는 **Leaf-wise(수직 성장)** 방식을 기본으로 사용합니다.

* **동작 원리**: 현재 존재하는 모든 리프 노드 중 **손실(Loss)을 가장 많이 줄여줄 수 있는 단 하나의 노드**를 탐욕적으로 선택해 분할합니다.
* **장점 (압도적 효율)**: 불필요한 노드까지 억지로 분할할 필요가 없어, 동일한 분할 횟수 대비 Level-wise보다 훨씬 빠르게 오차를 최소화합니다.
* **단점 (과적합 취약)**: 특정 가지(Branch)만 뱀처럼 비대칭적으로 깊어질 수 있어, 소수 샘플의 노이즈까지 전용 방(Leaf)을 만들어 외워버리기 쉽습니다.

## 5. 하이퍼파라미터 튜닝: 과적합 고삐 쥐기

Leaf-wise 구조에서는 트리가 깊어지는 형태가 자유롭기 때문에, `max_depth` 하나에 의존하기보다 **방의 총개수(`num_leaves`)와 방의 최소 정원(`min_data_in_leaf`)을 짝지어 조절**해야 합니다.

### 5-1. `num_leaves` vs `min_data_in_leaf` 직관
* **`num_leaves` (과적합 제어 1순위)**:
  * "트리 안에 **최종 방(Leaf)을 최대 몇 개까지 둘 것인가?**"
  * 트리의 깊이가 아무리 깊어져도 잎 노드의 총수를 묶어두면 전체 복잡도를 통제할 수 있습니다.
  * 완전 이진 트리의 잎 개수인 $2^{\text{max\_depth}}$보다 무조건 작게 잡는 것이 원칙입니다. (예: `max_depth=6`일 때 이론상 최대 64개이지만, `num_leaves=31` 정도로 제한)
* **`min_data_in_leaf` (`min_child_samples`)**:
  * "한 방에 **최소 몇 개의 데이터가 모여야 독립된 리프로 인정할 것인가?**"
  * 이 값이 너무 작으면 노이즈 데이터 1~2개만을 위한 뾰족한 과적합 잎이 파집니다.
  * 반대로 너무 크면 트리가 필요한 분할을 하지 못하고 언더피팅됩니다.

### 5-2. 데이터 규모별 `min_data_in_leaf` 실무 가이드라인

| 데이터 규모 | 권장 세팅 범위 | 튜닝 포인트 |
| :--- | :--- | :--- |
| **수천 ~ 수만 건** | 10 ~ 30 (기본값 20 권장) | 데이터가 적으므로 너무 키우면 트리가 자라지 못함 |
| **10만 ~ 100만 건** | 50 ~ 300 | 10만 건 중 우연히 뭉친 20개 노이즈를 학습하지 않도록 값을 상향 |
| **수백만 건 이상** | 수백 ~ 수천 단위 | 전체 데이터의 $0.01\% \sim 0.1\%$ 수준으로 통계적 유의성 확보 |
| **클래스 극심한 불균형** | 소수 클래스 수의 $1\% \sim 5\%$ | 소수 클래스를 분리해내는 잎 자체가 소멸하지 않도록 작게 세팅 |

> **💡 유효성 체크 팁:**  
> $\text{min\_data\_in\_leaf} \le \frac{\text{전체 훈련 데이터 수}(N)}{\text{num\_leaves} \times 2}$ 정도의 여유가 있어야 트리가 `num_leaves`로 지정한 개수만큼 방을 정상적으로 생성할 수 있습니다.

## 핵심 파라미터 매핑

| 파라미터 | 연결된 메커니즘 | 역할 및 튜닝 직관 |
| :--- | :--- | :--- |
| `num_leaves` | Leaf-wise 구조 | **트리 복잡도 통제의 1순위**. 클수록 표현력 증가, 작을수록 과적합 억제 |
| `min_child_samples`<br>(`min_data_in_leaf`) | Leaf-wise 안전장치 | 잎 노드의 최소 샘플 수. 훈련셋/검증셋 점수 격차가 벌어질 때 올려서 안정화 |
| `max_depth` | 수직 성장 한계선 | 보통 `num_leaves`로 제어하지만, 과적합이 심할 때 6~8 정도로 명시적 제한 |
| `learning_rate` ($\eta$) | 부스팅 축소율 | 새 트리의 반영 비율. 0.01~0.1 수준으로 낮추고 `n_estimators`를 넉넉히 준 뒤 Early Stopping 사용 |
| `colsample_bytree`<br>(`feature_fraction`) | 특성 샘플링 | 매 트리마다 사용할 피처 비율(0.7~0.9). 트리 간 다양성을 높여 분산 감소 |
| `subsample`<br>(`bagging_fraction`) | 데이터 샘플링 | 배깅 비율. GOSS 모드(`boosting_type='gbdt'`)가 아닐 때 데이터 과적합 완화 |

## 요약

1. **테이블 압축 (GOSS & EFB)**: 오차가 작은 샘플(행)은 가중치 보정으로 솎아내고, 겹치지 않는 희소 피처(열)는 오프셋으로 묶어 연산 대상을 대폭 줄였습니다.
2. **초고속 탐색 (Histogram)**: 정렬 없이 256개 안팎의 Bin 통계만 조회하여 메모리를 8bit로 절약하고 속도를 극한으로 끌어올렸습니다.
3. **비대칭 최적화 (Leaf-wise)**: 손실 감소가 가장 큰 리프만 골라 파고들어 적은 분할로도 최상의 성능을 내지만, 비대칭 과적합을 막기 위해 **`num_leaves`와 `min_data_in_leaf`를 세트로 제어**해야 합니다.

### Q&A

> [!question] LightGBM은 왜 작은 데이터셋(< 1만 건)에서 쓰면 과적합이 잘 날까요?
>
> 손실(Loss) 감소량이 최대인 잎 노드만 골라 파고드는 Leaf-wise 방식의 특성상, 데이터 양이 적으면 데이터 전체의 보편적인 규칙 대신 우연히 섞인 소수 샘플의 노이즈를 하나의 깊고 뾰족한 잎 노드로 외워버리기 쉽기 때문이다.

> [!question] 실무에서 XGBoost와 LightGBM은 어떤 기준으로 선택해야 할까요?
>
> 행 수가 수십만 건 이상이거나 피처가 많아 빠른 실험 사이클과 메모리 효율이 생명일 때는 **LightGBM**이 압도적이다. 반면 데이터셋 규모가 작고 정밀한 튜닝이나 엄격한 보수성이 요구될 때는 레벨 단위로 균형 있게 내려가 사후 가지치기를 수행하는 **XGBoost**가 안정적인 선택이 된다.
