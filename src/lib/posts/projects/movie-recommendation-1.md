# [모하시네마] 1. 영화 추천 서비스 - Vector DB 및 추천 시스템 아키텍처 설계

## 0. 프로젝트 개요

프로젝트 기간 : 2025.09.01 ~ 2025.09.29
프로젝트 인원 : 백엔드(3명), 프론트엔드(1명), 인프라(1명), AI(1명)
프로젝트 기여 :

- OpenAPI, 데이터 수집 파이프라인 구축
- EC2 싱글코어 상황에서 서버 부담을 줄이기 위해 Recall@K 기반으로 추천 시스템 성능을 유지하며 성능 부담 완화
- Two Tower 아키텍처 기반에서 Domain Mismatch를 해결하기 위한 MLP 레이어를 사용하여 추천 성능 강화
- 임베딩 시 데이터 절삭 및 누락 문제 해결을 위해 Multi Chunk 임베딩 및 Multi Field 임베딩을 통해 임베딩 성능 개선
- 자연어 질의를 LLM 대신 Sentence Transformer 기반 Zero-Shot 분류로 우선 처리하여 응답 시간 1.5초 개선

영화 추천 서비스 **모하시네마**를 개발하며 데이터 수집부터 임베딩 모델, Vector DB, 추천 시스템 아키텍처까지 결정했던 과정을 정리해보겠습니다.

프로젝트를 시작할 당시 팀원 대부분이 추천 시스템에 익숙하지 않았고, 약 한 달 안에 실제로 동작하는 결과물을 만들어야 했습니다. 따라서 가장 복잡하거나 성능이 높은 기술을 선택하기보다, 주어진 데이터 규모와 인프라 안에서 구현하고 운영할 수 있는 구조를 만드는 것을 우선시했습니다.

## 1. 프로젝트 요구사항과 제약조건

서비스는 사용자의 선호 장르와 영화 평가 이력, 자연어 질의를 바탕으로 영화를 추천하는 것을 목표로 했습니다. 이를 위해 다음 두 가지 추천 흐름을 구성했습니다.

1. 사용자의 평가 및 행동 로그를 활용한 추천
2. “에일리언 같은 영화 추천해줘”와 같은 자연어 질의를 활용한 추천

두 흐름 모두 사용자 정보를 벡터로 변환한 뒤 영화 벡터와 유사도를 비교해야 했습니다. 다만 짧은 개발 기간과 제한된 EC2 리소스 안에서 서비스를 운영해야 했기 때문에 다음 조건을 함께 고려했습니다.

- 다국어 영화 데이터를 처리할 수 있어야 한다.
- 영화 메타데이터와 벡터를 함께 관리할 수 있어야 한다.
- 별도 검색 인프라의 운영 부담을 최소화해야 한다.
- 싱글 코어 수준의 환경에서도 추천 API가 동작해야 한다.
- 사용자 로그 기반 추천과 프롬프트 기반 추천을 함께 제공해야 한다.

이 제약조건을 기준으로 데이터 수집, 임베딩 모델, Vector DB 및 추천 아키텍처를 순서대로 결정했습니다.

## 2. 데이터 수집 및 가공

### 2-1. 데이터 수집

영화 데이터는 `TMDB OpenAPI`를 중심으로 수집하고, 필요한 정보는 `KMDB`, `KOFIC`, `Wikipedia` 등의 데이터 소스를 추가로 활용했습니다. 수집 대상에는 영화 제목, 장르, 키워드, 출연진, 감독, 줄거리 등의 정보가 포함됐습니다.

초기 수집 단계에서는 약 200만 건의 원천 데이터를 확보했습니다. 이후, 중복 데이터와 서비스 대상이 아닌 데이터를 제거한 뒤, 실제 추천 검색에 사용하는 영화 데이터는 약 2만 건 이하로 추려냈습니다.

대량의 API 데이터를 수집하는 과정에서는 요청을 병렬로 처리하고 데이터를 청크 단위로 나누는 방식을 사용했습니다. 하지만, 수집 성공 여부와 빈 응답, 네트워크 오류를 충분히 구분하지 못해 누락된 데이터를 빠르게 확인하기 어려웠습니다

프로젝트 진행 후, 데이터의 정합성과 퀄리티를 위해 데이터 수집 시 아래 사항들을 체크하는 것이 중요합니다.

- 요청 성공 및 실패 상태
- HTTP 오류 코드와 재시도 횟수
- 데이터 소스별 수집 건수
- 빈 응답과 실제 결측값의 구분
- 실패 데이터 재처리 대상

### 2-2. 데이터 가공

추천에 사용할 데이터는 다음과 같은 형태로 정리했습니다.

```json
{
  "title": "프로메테우스",
  "genres": ["SF", "스릴러"],
  "keywords": ["우주선", "외계인"],
  "overview": "2085년, 인류의 기원을 찾기 위해 탐사대가 우주로 향한다."
}
```

API에서 수집한 `Keywords` 데이터에는 결측값이 많았고 일부 키워드는 영화의 특성을 충분히 설명하지 못했습니다. 키워드는 사용자 질의와 영화를 연결하는 중요한 Feature이기 때문에 임베딩 전에 데이터를 보완해야 했습니다.

처음에는 다음과 같은 자동화 방법을 진행했습니다.

1. 전체 키워드를 출현 빈도와 함께 수집한다.
2. `K-Means`, `DBSCAN`, `Hierarchical Clustering`으로 유사한 키워드를 군집화한다.
3. 각 Cluster의 대표 키워드를 메타데이터로 만든다.
4. 대표 키워드를 활용해 결측값을 자동으로 태깅한다.

`K-Means`는 군집 개수를 지정해줘야 했습니다. 하지만, 적절한 Cluster 개수를 결정하기 어려워 사용하지 않았습니다. `DBSCAN`과 `Hierarchical Clustering`은 일부 키워드를 묶을 수 있었지만 각 Cluster를 하나의 대표 키워드로 압축하기 어려웠습니다. `Overview`에 TF-IDF를 적용하는 방법도 시도했으나, 줄거리에 영화의 핵심 키워드가 직접 등장하지 않는 경우가 있었기에 사용하지 않았습니다.

결국 기존 약 20,000개의 키워드를 군집화한 결과를 검수해 유의미한 키워드 메타데이터를 만들었습니다. 이후 `Overview`에서 패턴 매칭을 수행해 비어 있는 키워드를 보완습니다.

이 과정에서 모델링이 반드시 전체 작업의 자동화를 의미하지는 않는다는 점을 느꼈습니다. 자동화된 결과의 품질이 일정하지 않다면, 모델을 사람이 검수해야 할 범위를 줄이는 도구로 활용하는 방식이 낫다고 생각했습니다.

## 3. Vector DB 선택

Vector DB를 선택할 때 고려한 조건은 다음과 같습니다.

1. 데이터 규모와 검색 성능
2. 운영 복잡도
3. 검색 정확도와 인덱싱 방식
4. 영화 메타데이터와 벡터의 관리 방식

원천 데이터는 약 200만 건이었지만 실제 서비스에서 벡터 검색에 사용하는 데이터는 약 2만 건이었습니다. 이 정도 규모에서는 별도의 Vector DB를 추가해 아키텍처를 복잡하게 만들기보다, 서비스 DB와 벡터 저장소를 하나로 관리하는 편이 적합하다고 판단했습니다.

따라서 기존에 고려했던 MySQL 대신 PostgreSQL을 사용하고, PostgreSQL에서 벡터 검색을 지원하는 `pgvector`를 적용했습니다.

이 선택을 통해 영화의 장르, 키워드, 개봉 연도 같은 관계형 데이터와 임베딩 벡터를 하나의 데이터베이스에서 관리할 수 있었고, 메타데이터 필터링과 벡터 유사도 검색을 하나의 SQL 안에서 처리할 수 있어 별도의 검색 시스템을 운영하는 부담을 줄일 수 있었습니다.

## 4. 임베딩 모델 선택

영화 데이터와 사용자 질의를 같은 벡터 검색 과정에서 사용하기 위해 임베딩 모델을 선택했습니다. 주요 고려사항은 다음과 같습니다.

1. 다국어 지원 여부
2. 입력할 수 있는 텍스트 길이
3. 출력 벡터의 차원 수
4. 제한된 환경에서의 실행 비용

후보 모델은 다음과 같습니다.

| 모델 | 벡터 차원 | 특징 |
| --- | ---: | --- |
| Multilingual E5 Small | 384 | 다국어 지원, 상대적으로 작은 벡터 크기 |
| Multilingual E5 Large | 768 | 더 큰 모델과 벡터 크기 |
| text-embedding-3-small | 1536 | 외부 API 방식 |
| text-embedding-3-large | 3072 | 외부 API 방식, 큰 벡터 크기 |
| text-embedding-004 | 768 | 외부 API 방식 |

TMDB 데이터에는 여러 언어가 포함되어 있어 다국어 처리가 필요했고, 운영 환경의 메모리와 CPU 사용량을 고려하면 벡터 차원도 중요한 조건이었습니다. 또한, 임베딩 시 커스텀을 자유자재로 할 수 있다는 점에서 `multilingual-e5-small`을 선택했습니다.

## 5. 데이터 임베딩 방식

### 5-1. 임베딩 입력 형식

E5 모델은 동일한 모델에서 질의와 문서를 구분하기 위해 입력 앞에 prefix를 추가했기에, 임베딩 시 사용자 질의에는 `query:`, 영화 데이터에는 `passage:`를 사용하여 임베딩을 수행했습니다.

```text
query: 에일리언 같은 SF 영화 추천해줘

passage: title 프로메테우스, genre SF 스릴러, keyword 우주선 외계인, overview ...
```

### 5-2. 임베딩 입력 절삭 문제

처음에는 영화의 제목, 장르, 키워드, 줄거리를 하나의 텍스트로 연결한 뒤 한 번에 임베딩하는 방식을 사용했습니다.

```json
{
  "passage": {
    "title": "프로메테우스",
    "genre": ["SF"],
    "keyword": ["우주", "외계인"],
    "overview": "2085년, 인류의 기원을 찾기 위해 탐사대가 우주로 향한다."
  }
}
```

영화 메타데이터를 바로 임베딩을 진행하는 경우 영화마다 보유한 필드가 달랐고, 토큰 수 제한이 512이므로 입력의 크기가 제한되어 데이터가 절삭되는 문제가 발생했습니다.

문제 상황을 다음의 2가지 Case로 분류해서 문제를 해결했습니다.

* 한 Field의 텍스트 길이가 길어서 한 Field의 Data가 소실되는 경우.
* 전반적인 Field의 길이가 길어서 여러 Field의 Data가 절삭되는 경우.

첫 번째 케이스의 경우에는, `Overview`같이 텍스트 길이가 긴 경우 필드 순서를 조정해서 일부 문제를 완화할 수 있었습니다.
두 번째 케이스 전체 필드 길이가 긴 경우 맨 뒤에 놓이는 Field가 `truncate` 되는 문제가 발생했습니다. 즉, `Overview` Field가 절삭되는 문제가 발생해서 Query에 줄거리를 넣는 경우 제대로 동작하지 않았습니다. 정제된 데이터의 평균 토큰 수는 약 250 Token이고, 약 1천건 정도는 줄거리가 매우 길어서 `truncate` 되었습니다.


### Case 1 Solution : Multi Filed Embedding

이를 보완하기 위해 단일 임베딩에서는 각 Field를 Embedding 시킨 후, `Concat`이나 `Mean Pooling`, `Attention Pooling`을 사용해서 해결할 수 있습니다. 이 방식을 사용하는 경우 `Overview`처럼 `query`의 마지막에 주어져 `truncate`되는 문제를 해결할 수 있고, `genre`나 `title`처럼 짧은 쿼리들을 강조할 수 있습니다.

하지만, `Semantic Drift` 해결을 위해 `document` 반복을 과도하게 할 경우 저품질의 데이터로 채워져 정보가 `Dilution` 되는 문제가 발생했습니다. 성능 체크는 `Recall@K` 를 사용해서 지표를 확인하는 것이 좋지만, 불가능한 경우 2~3회정도로 제한한합니다.

```json
Before
{
  "title" : "프로메테우스",
  "genre" : ["SF", "스릴러"],
  "keyword" : ["우주선", "외계인"],
  "overview" : "2085년. 인간이 외계인의 유전자 조작을 통해 탄생한 생명체라는 증거들이 속속 발견되면서 인류의 기원을 찾기 위해 탐사대가 꾸려진다..."
}

After
{
  "title" : "프로메테우스",
  "genre" : ["SF", "스릴러", "SF", "스릴러"],
  "keyword" : ["우주선", "외계인", "우주선", "외계인"],
  "overview" : "2085년. 인간이 외계인의 유전자 조작을 통해 탄생한 생명체라는 증거들이 속속 발견되면서 인류의 기원을 찾기 위해 탐사대가 꾸려진다..."
}
```

`Multi Field Embedding`은 어떻게 해야할까?' 라는 물음을 해결하기 위해 다음의 3가지 방법을 고려했습니다.

1. Field별 Embedding 이후 Concat으로 벡터 생성
2. Field별 Embedding 이후 Mean Poooling으로 벡터 생성
3. Field별 Embedding 이후 Attention Pooling으로 벡터 생성

`Mean Pooling`의 경우 feature간 관계 학습이 사라지는 문제가 발생할 수 있습니다. `Concat`의 경우, 구현은 조금 복잡할 수 있지만, 각 Field별 Weight를 조정하면서 학습 진행이 가능하고 데이터 소실 위험이 낮다는 장점이 있습니다. 구현이 조금 어려워지겠지만, `Concat` 으로 임베딩을 진행하는 것이 더 좋은 성능을 낼 수 있습니다.

### Case 2 Solution : Multi Chunk Embedding

긴 `Overview`가 절삭되어 정보 손실이 발생하는 경우에는 `Multi Chunk Embedding`을 적용할 수 있습니다. 이 경우 각 `Overview`의 길이가 다르기 때문에 `Concat`을 진행하는 경우 벡터의 크기가 각각 다를 수 있습니다. 이 때문에, `Multi Chunk Embedding`의 경우에는 `Mean Pooling` 또는 `Weighted Pooling` 을 사용하여 문제를 해결했습니다.

또한, `Overlap`을 사용해서 겹치는 구간을 남겨두어서 의미 손실을 방지했습니다. Overview를 일정 길이로 분할하고, 10~20% 정도의 `Overlap`을 둬 문맥 손실을 방지했습니다. `Sentence Transformer`는 문맥 의존적이므로 중간에 절삭되는 경우 의미가 왜곡되어 이를 방지해야합니다.


```json

Before
{
```

`Multi Chunk Embedding`의 경우에 줄거리의 중요한 부분을 자동으로 파악하기 위해 `Attention Pooling`을 사용하는 것이 좋고,  한 Row에 대해 `Multi Field Embedding`을 사용하는 경우에는 중요한 `Field`를 강조하기 위해서 `Weighted Pooling`을 사용하는 것이 좋습니다.

결론적으로, Row 수준에서는 `Multi Field Embedding` → Weighted Pooling, 문장 수준에서는 `Multi Chunk Embedding` → Attention Pooling 이 조합이 정보 손실을 최소화하면서 의미 보존과 효율성을 모두 확보할 수 있었습니다. 한 `Field` 내에서 동작하는 `Multi Chunk Embedding`의 경우에 문맥의존적인 `Attention Pooling`을 사용하는 것이 좋을 수 있습니다.
