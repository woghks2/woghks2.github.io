# [던통] 게임 통계 서비스 - 3. API 호출량 최적화

## 1️⃣ API 호출량 문제

단순히 검색을 통해서 OpenAPI에 존재하는 데이터를 보여주는 것에 더해, 수집한 데이터를 집계하고 분석하여 사용자에게 의미있는 데이터를 제공하는 것이 중요합니다.

300만개가 넘는 데이터 전체를 매일 리프레시 하려면 약 3천만 건의 API 요청이 발생합니다. 그런데 Neople OpenAPI는 초당 1000건의 요청을 제한하고 있어서, 3천만 건을 전부 처리하려면 3만 초, 즉 8시간이 넘는 시간이 필요합니다. 하나의 태스크를 긴 시간동안 진행하는 경우 다음의 문제가 발생할 수 있습니다.

- **시간**: 호출 시간이 길어질수록 파이프라인이 그만큼 오래 열려있어야 하고, 하루 배치 안에 안정적으로 끝난다는 보장이 약해집니다.
- **외부 장애 취약성**: 요청 하나하나는 가볍지만, 8시간 동안 3천만 건을 쏘다 보면 네트워크 오류·외부 서비스 장애·서버 오류가 누적될 가능성이 커지고, 오류가 발생했을 때 재처리해야 할 대상도 함께 커집니다.

그렇다고 호출 속도를 올려서 시간을 줄이는 것도 답이 아니었습니다. 초당 API 호출량 제한과 더불어 내부 병렬 처리 등 다양한 항목에서 이미 제한을 받고 있었고, 제한에 근접할수록 오류 리스크만 커지는 구조였습니다.

## 2️⃣ 데이터 신선도

그럼 발상을 바꿔서 '모든 데이터를 다 매일 갱신할 필요가 있을까?'라는 생각을 했습니다. 여기서 주목한 건 데이터마다 신선도(Data Freshness) 요구 수준이 다르다는 점이었습니다. 데이터 신선도란 저장된 데이터가 실제(원본) 값과 얼마나 최근 상태로 일치하는지를 나타내는 정도로, 신선도가 낮다(stale하다)는 건 마지막 갱신 이후 시간이 많이 지나 원본과 값이 달라졌을 가능성이 있다는 뜻입니다. 캐릭터 300만 건이 전부 똑같은 무게로 화면에 노출되는 게 아니라면, 굳이 전부를 같은 주기로 갱신할 이유가 없다고 판단했습니다.

분산 시스템 관점에서 보면 데이터 신선도를 다루는 방식은 크게 세 가지로 나뉩니다.

| 모델 | 설명 |
| --- | --- |
| Strong Consistency (강한 일관성) | 갱신되면 즉시 모든 곳에서 최신 값만 보이도록 보장. 신선도 요구가 가장 빡빡한 모델. |
| Eventual Consistency (최종적 일관성) | 언젠가는 최신 값으로 수렴하지만, 그 시점은 보장하지 않음. |
| Bounded Staleness (제한적 신선도) | "최대 N만큼만 오래된 데이터를 허용한다"고 상한을 명시적으로 정해두는 모델. |

300만 건이 넘는 데이터가 전부 똑같은 중요도를 가지는 것이 아니라면, 굳이 전부를 같은 주기로 갱신할 이유가 없다고 판단하여 요구사항 분석을 통해 던통 서비스 데이터의 신선도에 대해서 알아보았습니다. 개별 캐릭터의 경우 상세 페이지에 도달할 경우 자동으로 업데이트 되어 단일 캐릭터에 대해서는 문제되는 것이 없었습니다.

하지만, 직업 통계 페이지에서 사용자에게 유의미한 정보를 주는 대상은 각 직업별 **상위 10% 캐릭터**였습니다. 하위권 캐릭터는 통계에 섞이면 유의미한 정보나 랭킹 순위와 같은 정보에 부정확한 정보를 주기 때문에 매일 최신 상태일 필요성도 낮았습니다. 반대로 상위권 캐릭터는 통계 결과를 그대로 좌우하기 때문에, 여기서 stale한 데이터를 쓰면 서비스 신뢰도에 바로 영향을 줍니다.

## 3️⃣ 활동 기반 갱신

최근 활동이 있었던 캐릭터만 갱신 대상으로 선정하는 방식도 고려했습니다. 이러한 경우, 액티브 캐릭터만 집계하여 갱신하므로 효율적으로 진행할 수 있습니다.

하지만 해당 게임 서비스의 시즌 초, 신규 캐릭터 출시, 대규모 패치 시점에 활성 유저 규모가 크게 변합니다. 활동 유저를 기준으로 시즌 초에 성수기 약 30만 명인 데이터가 현재 약 8만 명대로 줄어들었습니다. 이 변동폭을 그대로 반영하면 성수기에는 갱신 대상이 오히려 지금보다 커져 API 호출량 상한을 예측할 수 없고, 비수기에는 반대로 갱신 대상이 지나치게 줄어들어 통계 표본 자체가 부실해질 위험이 있습니다.

즉, "얼마나 갱신할지"를 서비스가 아니라 유저 활동량이 결정하게 되는 구조라, 호출량을 안정적으로 관리하려는 원래 목적과 맞지 않았습니다.

## 4️⃣ 문제 해결

앞선 활동 기반 갱신의 단점으로 인해, 현재 사용하던 Strong Consistency 대신 Bounded Staleness를 채택하여 순환 갱신 방식을 사용하기로 했습니다. 던통 서비스에서는 매주 주간 집계를 진행하기 때문에 제한적 신선도를 7일로 제한하여 주간 집계 시 stale한 데이터가 발생하지 않도록 했습니다.

- **상위 10% (약 30만 건)**: 매일 갱신 → 하루 약 300만 건 요청
- **나머지 90%**: 6일에 걸쳐 하루 15%씩 순환 갱신 → 7일 안에 전체 캐릭터가 최소 한 번은 갱신

상위권 데이터는 매일 최신 상태를 유지하고, 나머지 데이터는 최대 7일 이내에는 반드시 한 번 갱신되도록 순환시켜서, 주간 단위로 집계를 돌리더라도 특정 캐릭터의 데이터가 일주일 이상 stale한 상태로 방치되는 일이 없도록 했습니다.

결과적으로, 하루 3천만 건이 넘던 API 요청을 1천만 건 수준(전체 대비 약 25%)으로 줄였고, 파이프라인 소요 시간도 8시간에서 2시간 이내로 단축할 수 있었습니다.

## 5️⃣ 회고

처음에는 단순히 "API 호출량을 어떻게 줄일까?"에만 집중하여 초당 제한, 병렬 처리, 재시도 전략 같은 기술적인 최적화만 고민해서 시간을 단축하려고 했습니다.

그런데 문제를 파고들다 보니, 본질은 호출량 자체가 아니라 '모든 데이터를 같은 신선도로 유지할 필요가 있는가?'라는 질문이 핵심이었습니다.

App DB에서는 거의 Strong Consistency에 가까운 신선도가 필요하지만, 통계와 집계를 담당하는 DM/DW 영역에서는 Bounded Staleness를 허용해도 서비스 품질에 큰 영향이 없다는 차이를 인지하고, 상위 10%는 매일, 나머지는 7일 순환 갱신으로 설계하니 호출량을 약 75% 줄이면서도 주간 집계의 신뢰도를 유지했습니다.

이번 작업을 통해 파이프라인 최적화가 빠르고 많이 처리하는 것이 전부가 아니라는 것을 배우며 데이터의 성격과 사용 목적에 맞는 신선도 수준을 먼저 정의하는 것이 기술적인 최적화보다 의미있는 효과를 낼 수 있다는 것을 배웠습니다.
