# **BM 구매 예측 및 CRM 타겟 설계**

## 프로젝트 요약

> 현재 신규 캐릭터 전용 패키지 구매자의 활동 패턴을 학습하고, 다음 유사 BM 출시 시 구매 가능성이 높은 유저를 선별해 CRM 타겟 우선순위를 설계한 프로젝트입니다.
> 

<aside>

- Test Recall 78.2%로 실제 구매자의 상당 부분을 포착
- Precision 45.0%로 전체 평균 구매율 33.9%보다 높은 타겟 구매율 확보
- PR-AUC 0.5217로 구매자 클래스 ranking 성능이 baseline 대비 개선
- 구매 가능성 점수 상위 20%의 구매율 56.1%, Lift 1.66배
</aside>

## 1. 문제 정의

게임 서비스에서 리텐션이 하락하면 자연스럽게 매출 하락 가능성이 증가합니다. 신규 콘텐츠나 신규 캐릭터 출시 시점에는 유저의 복귀와 결제를 함께 유도할 수 있는 BM이 출시되지만, 전체 액티브 유저를 동일하게 대상으로 삼는 CRM은 효율이 낮습니다. 따라서 전체 액티브 유저에게 일괄 메시지를 보내는 것보다,  **구매 가능성이 높은 유저를 우선 선별**하는 것이 문제입니다.

즉, 이 프로젝트의 목표는 단순히 패키지를 구매를 예측하는 것이 아니라, 현재 패키지 구매 데이터를 학습해 **다음 유사 BM 출시 시 CRM 타겟 우선순위**를 설계하는 것입니다.

정리하면 문제는 다음과 같습니다.

<aside>

- 현재 상황: 리텐션 하락 이후 매출 회복을 위해 신규 캐릭터 전용 BM 패키지 판매가 중요해짐
- 비즈니스 제약: 신규 캐릭터를 생성한 유저만 해당 패키지를 구매할 수 있음
- CRM 목표: 구매 가능성이 높은 유저를 먼저 선별해 캠페인 비용과 노출 기회의 효율적 사용
- 모델 목표: 유저 데이터를 기반으로 패키지 **구매 가능성 점수**를 산출하고 CRM 타겟 우선순위 구성
</aside>

## 3. 피처 설계 및 평가 설계

피처를 설계하면서 발생한 문제는 다음과 같습니다.

### 3-1. 다중공선성 문제

유저의 활동 로그를 기반으로 콘텐츠 클리어 기록과 캐릭터 스펙을 피처로 변환했습니다. 제한된 데이터로 feature를 설계했기에 feature끼리 높은 상관 관계를 가지는 문제가 발생했습니다. 높은 상관 관계로 인해 발생할 수 있는 문제는 다음과 같습니다.

<aside>

- 파생변수 또한 상관관계가 높은 문제가 발생
- 차원의 저주: 불필요한 피처 수 증가로 학습 시간 및 메모리 증가
- 과적합 위험: 중복 정보를 학습하면서 노이즈까지 학습할 여지 증가
- 선형 모델을 사용하는 경우 다중공선성 문제 (VIF) 발생 위험 및 선형성, 등분산성 등 가정 필요
- 트리 모델을 사용하는 경우, Feateure Importance가 여러 feature에 분산되는 문제가 발생
</aside>

간단한 비교 실험을 통해 `Logistic Regression` 및 `SVM`에 규제화를 적용해 실험했으나 저조한 성능을 보여주어 모델 후보에서 제외했습니다. 이 때문에 선형 모델보다 트리 기반 모델이 적합하다고 판단했습니다.

### 3-2. 데이터 불균형 문제

BM을 구매하는 유저는 전체 유저에 비해 비율이 낮은 형태를 띄고 있습니다. 이를 고려하지 않고 학습을 진행하는 경우 발생할 수 있는 문제는 다음과 같습니다

<aside>

- 다수 클래스에 대한 예측 편향이 발생
- 소수 클래스에 대해 과적합 발생
- 결정 경계 왜곡 및 일반화 성능 저하
</aside>

이러한 데이터 불균형 문제는 모델 선택과 학습, 평가 지표와 밀접한 연관이 있기에 다음 파트에서 설명을 진행하겠습니다.

### 3-3. 평가 설계

구매 유저 비율은  극단적인 불균형은 아니지만 약간의 불균형이 존재하는 33.9% 입니다. CRM 관점에서는 구매자를 최대한 많이 포착하는 것이 중요하기에 Accuracy보다 다음의 지표를 중점적으로 확인했습니다.

<aside>

- **Recall**: 실제 구매자 중 모델이 타겟으로 포착한 비율
- **Precision**: 타겟으로 선정한 유저 중 실제 구매자 비율
- **F1**: Precision과 Recall의 균형
- **PR-AUC**: 구매자 클래스에 대한 ranking 품질
- **Lift@K**: 점수 상위 K%의 구매율이 전체 평균 대비 얼마나 높은지
</aside>

Threshold는 test set에서 고르지 않고 validation set에서 선택했습니다. Test set은 선택된 최종 모델의 일반화 성능을 확인하는 용도로만 사용했습니다.

CRM에서는 특정 threshold 하나만 보는 것보다, 상위 10%, 20%, 30%처럼 타겟 규모를 정하기 위해 Top-K 지표도 함께 계산했습니다.

## 4. 모델 선택 및 학습

### 4-1. 모델 선택

학습에 사용할 수 있는 모델은 많지만 앞선 feature의 특성을 고려하여 트리 기반 모델 중에서도 앙상블 방식이 다른 3개를 비교했습니다.

- **RandomForest**: 여러 트리를 독립적으로 병렬 학습(bagging) 후 평균/투표로 결합하는 방식으로 분산을 줄여 과적합에 상대적으로 강건함
- **XGBoost**: 같은 깊이의 모든 노드를 먼저 분기시킨 후 다음 깊이로 내려가는 **Level-Wise** 방식으로 트리 구조가 균형 잡혀 있어 상대적으로 안정적이고 과적합 위험이 낮지만, 불필요한 분기까지 만들 수 있어 LightGBM보다 학습 속도가 느림.
- **LightGBM**: 손실을 가장 많이 줄이는 리프를 우선적으로 분기하는 **Leaf-Wise** 방식으로 같은 리프 개수 대비 손실을 더 적극적으로 줄여 정확도가 높고 학습 속도도 빠르지만, 트리가 비대칭적으로 자랄 수 있어 과적합 위험이 XGBoost보다 상대적으로 큼.

### 4-2. 불균형 처리 전략 선택

불균형 처리는 모델 선택 이후에 따로 붙이는 요소가 아니라, 모델의 학습 방식과 함께 성능에 영향을 주기에 모델과 불균형 전략을 동시에 비교했습니다.

- **Vanilla**: 별도 불균형 처리 없이 원본 데이터 그대로 학습
- **Class Weight**: 손실 함수에서 소수 클래스(구매자)의 오분류 패널티를 높여, 데이터를 변형하지 않고 학습 방식만 조정하는 방법
- **SMOTE**: 소수 클래스 샘플 간 보간을 통해 가상의 합성 샘플을 생성, 소수 클래스 데이터 양 자체를 늘리는 방법

### 4-3. 모델 학습

3개의 모델(RandomForest, LightGBM, XGBoost)과 3개의 불균형 전략(Vanilla, Class Weight, SMOTE)을 조합하여 총 9개의 모델을 학습하여 1차 스크리닝을 진행했습니다.

피처는 모델 입력 전 Train/Validation/Test를 먼저 분리하고, 스케일링은 학습 파이프라인 내부에서만 적용했습니다. SMOTE를 사용하는 경우에도 validation/test 정보가 섞이지 않도록 CV train fold 내부에서만 적용했습니다.

Stage 1에서는 동일한 split과 동일한 validation 기준으로 9개 조합을 비교했습니다.

| 모델 | 불균형 전략 | Threshold | Recall | Precision | F1 | PR-AUC | Lift@20% |
| --- | --- | --- | --- | --- | --- | --- | --- |
| RandomForest | Vanilla | 0.30 | 79.3% | 44.7% | 0.5720 | 0.5370 | 1.70x |
| RandomForest | Class Weight | 0.40 | 84.6% | 43.3% | 0.5729 | 0.5364 | 1.69x |
| RandomForest | SMOTE | 0.30 | 82.9% | 43.7% | 0.5724 | 0.5385 | 1.70x |
| LightGBM | Vanilla | 0.30 | 78.5% | 45.4% | 0.5754 | 0.5408 | 1.70x |
| LightGBM | Class Weight | 0.45 | 78.8% | 45.2% | 0.5746 | 0.5430 | 1.71x |
| **LightGBM** | **SMOTE** | **0.35** | **74.6%** | **46.7%** | **0.5744** | **0.5428** | **1.72x** |
| XGBoost | Vanilla | 0.30 | 78.7% | 45.5% | 0.5764 | 0.5423 | 1.71x |
| **XGBoost** | **Class Weight** | **0.45** | **78.5%** | **45.4%** | **0.5749** | **0.5438** | **1.72x** |
| **XGBoost** | **SMOTE** | **0.30** | **82.0%** | **44.3%** | **0.5752** | **0.5466** | **1.72x** |

Stage 1 결과만 보면 XGBoost + SMOTE의 PR-AUC가 가장 높았습니다. 다만 SMOTE는 보간을 활용하여 합성 샘플을 생성하기 때문에 운영 환경에서 해석이 복잡해질 수 있습니다. 또한, 정수형 데이터의 경우 합성 샘플이 실제 존재하지 않는 데이터가 만들어질 수 있습니다.

하지만, XGBoost + Class Weight는 성능 차이가 작고, threshold가 0.45로 상대적으로 중앙에 가까우며, 구매자 클래스 가중치를 직접 반영하는 단순한 방식입니다. 따라서 Stage 2에서는 상위 후보 3개를 대상으로 튜닝을 수행하고, 최종 모델은 `XGBoost + Class Weight`로 고정했습니다.

### 5-2. CRM 적용

Threshold 기반 분류 결과도 중요하지만, 예산과 발송량이 먼저 정해지는 경우가 많기에 구매 가능성 점수 기준 상위 K%를 잘라 타겟군의 구매율과 Lift를 계산했습니다.

## 6. 프로젝트 회고

이전에는 모델을 구축하고 성능 지표를 확인하는 데 그쳤다면, 이번 프로젝트에서는 모델 점수를 CRM 타겟 우선순위로 전환하는 방식까지 고민했습니다. 특히 Threshold 기반 분류 성능뿐 아니라 Top-K, Lift, 구매자 포착률을 함께 보면서 ‘모델이 실무에서 어떤 의사결정에 쓰일 수 있는가’를 정리할 수 있었습니다.

피처 설계 측면에서 개선할 부분이 있었습니다. OpenAPI에서 제공되는 유저의 활동 로그가 제한되어 있어서 동일한 유저 활동에서 피처를 생성했기에 파생 변수간 상관 관계가 높은 구조였습니다. 이 떄문에, 불필요하게 과도한 feature를 학습하거나 중복 정보를 학습하게 되어 `feature importance`가 분산되어 해석에 어려움을 겪을 수 있습니다.  추후에는 실제 성능에 기여하는 그룹을 확인하고, correlation clustering이나 permutation importance를 활용해 `중복된 데이터를 줄이고 feature importance 해석력을 높이는 방향으로 개선하고 싶습니다.`

피처 개선과 별개로, 모델 성능과 CRM 적용 관점에서도 보완할 지점이 있었습니다. 모델의 성능은 Test Recall 78.2%, Top 20% Lift 1.66배로 무작위 타겟팅 대비 구매 가능성이 높은 유저를 선별할 수 있음을 확인했습니다. 하지만 Precision 45.0% 수준은 타겟 유저의 절반 이상이 실제로는 구매하지 않는다는 의미이므로, 현재의 Validation F1 기준 threshold를 그대로 CRM에 적용하기보다는 비용 관점을 반영한 기준으로 보완할 필요가 있다고 판단했습니다.

현재는 Validation F1을 기준으로 threshold를 선택했지만, F1은 precision과 recall의 균형만 반영할 뿐 실제 CRM 집행에 드는 발송 비용, 쿠폰 비용이나 기대 구매액은 고려하지 않습니다. 추후에는 캠페인 예산과 유저 1인당 쿠폰 비용을 먼저 설정한 후, 이 예산 제약 안에서 순이익(예상 구매액 − 발송/쿠폰 비용)을 최대화하는 threshold나 Top-K를 계산하는 방식으로 개선하고 싶습니다. 다음 실험에서는 `성능 지표뿐만 아니라 비용 기반 threshold, 캠페인 예산별 Top-K 등 의사결정 지표를 함께 비교`하고자 합니다.
