# [던통] 게임 통계 서비스 - 2. 데이터 플랫폼 구축: 데이터 파이프라인 만들기

## 0. 프로젝트 개요

프로젝트를 개발하면서 초기 개발단계를 지나, 데이터를 효율적으로 수집하고 분석할 수 있는 데이터 플랫폼을 구축했습니다. Airflow를 활용해서 데이터 수집 작업을 자동화하고, 데이터를 Google Cloud Storage에 저장하고, BigQuery에 적재하는 파이프라인을 구축했습니다. 이번에는 Airflow를 통해서 데이터 파이프라인을 만들면서 발생한 문제점과 해결 방법을 포스팅했습니다.

## 1. 데이터 수집 규모 설계

### 1-1. API 호출량 문제

단순히 검색을 통해서 OpenAPI에 존재하는 데이터를 보여주는 것에 더해, 수집한 데이터를 집계하고 분석하여 사용자에게 의미있는 데이터를 제공하는 것이 중요합니다.

좌측의 사진처럼 약 3백만건이 넘는 캐릭터들을 매일 집계하여 우측 사진처럼 매일 사용자에게 업데이트된 통계 정보를 제공해야했습니다. 이 과정에서 매일 수천만건의 데이터를 수집하고, 이를 집계하여 사용자에게 의미있는 데이터를 제공하는 파이프라인을 구축했습니다.

이 과정에서 저장된 데이터를 업데이트하지 않는 경우 집계 시 stale한 데이터를 집계하여 서비스의 신뢰도에 영향을 끼칠 수 있습니다. 이를 해결하기 위해 캐릭터 상세 페이지에 사용자 요청이 들어올 때만 리프레시 하는 것이 아니라 배치 처리를 통해 리프레시 된 데이터를 유지하는 것이 중요합니다.

캐릭터 데이터를 집계해 직업별 통계를 제공하려면, 캐릭터 한 건당 기본 정보·장비·스킬·서약 등 연관된 API 10개 이상을 호출해야 했습니다.

캐릭터 수 자체는 약 300만 건으로 크지 않았지만, 캐릭터마다 API를 호출하면 전수 갱신 시 하루에 약 3천만 건이 넘는 API 요청이 발생하는 규모였습니다.

요청 하나하나는 가볍더라도 대량의 데이터를 매일 처리하려면 네트워크 오류, 외부 서비스 장애, 서버 오류가 누적될 가능성이 커지고 오류가 발생했을 때 재처리해야 할 대상도 함께 커졌습니다. 모든 데이터를 매일 갱신하는 방식으로는 파이프라인을 안정적으로 운영하기 어려웠습니다. 1초당 1천건의 API 요청 제한이 있었기에 속도에 상한선이 존재했고, 이에 근접할수록 오류 리스크는 커지는 상황이었습니다.

이를 해결하기 위해 요구 사항에 맞추어 화면에 보여지는 데이터부터 우선 갱신하는 방식으로 전환했습니다. 직업 통계 페이지에서 유의미한 정보를 제공하는 대상은 각 직업별 상위 10% 캐릭터라는 요구사항을 고려하여, 다음과 같이 갱신 주기를 나눴습니다.

- **상위 10% (약 30만 건)**: 매일 갱신 → 하루 약 300만 건 요청
- **나머지 90%**: 6일에 걸쳐 하루 15%씩 순환 갱신 → 7일 안에 전체 캐릭터가 최소 한 번 갱신됨

이 방식으로 하루 3천만 건이 넘는 API 요청을 1천만 건 수준으로 줄이면서도, 화면에 노출되는 상위권 데이터는 매일 최신 상태를 유지했습니다. 나머지 데이터도 최대 7일 이내에는 갱신되도록 순환시켜, 특정 캐릭터의 데이터가 일주일 이상 stale한 상태로 방치되지 않도록 했습니다.

## 2. 네트워크 응답 분류 표준화

### 2-1. 데이터 정합성 문제

파이프라인 초기에는 실패가 잦아 백필을 자주 수행해야 했습니다. 문제는 백필을 실행할 때마다 스크립트별로 API 응답을 처리하는 방식이 달랐다는 점이었습니다.

- 어떤 스크립트는 HTTP 상태 코드만으로 성공/실패를 판단했고
- 어떤 스크립트는 오류 응답 body의 DNF 자체 오류 코드는 확인하지 않아, 실제로는 실패한 요청을 성공으로 처리하는 경우가 있었으며
- 빈 데이터(활동 없음)와 실제 오류를 구분하지 않고 둘 다 실패로 기록하는 경우도 있었습니다

그 결과 같은 원인의 실패인데도 스크립트마다 재처리 대상으로 잡히거나 잡히지 않는 등 데이터 일관성 문제가 발생했습니다. 백필을 돌릴 때마다 "이 캐릭터가 진짜 실패였는지, 원래 빈 데이터였는지"를 다시 확인해야 했습니다.

### 2-2. 응답코드 표준화

이를 해결하기 위해 API 호출 결과를 판단할 때 HTTP 상태 코드만 확인하지 않고, 오류 응답 body의 DNF 자체 오류 코드까지 함께 파싱해 최종 결과를 분류하도록 표준화했습니다. 캐릭터가 존재하지 않거나 활동이 없는 경우도 "오류"가 아니라 "정상적인 빈 결과"로 별도 처리했습니다.

| 분류 | 의미 | 후속 처리 |
| --- | --- | --- |
| `done_success` | 유효한 응답이며 상세 데이터가 존재 | 정상 적재 |
| `done_empty` | 유효한 응답이지만 활동이 없음 | 실패로 보지 않고 정상 종료 |
| `done_missing` | 캐릭터나 아이템이 원천에서 사라짐 | 허용 가능한 결과 없음으로 기록 |
| `retryable_error` | 429, 5xx, 일시적 네트워크 오류 등 | 실패 대상만 재처리 |
| `hard_failed` | 파싱 오류, schema 불일치, DNF 오류 코드 등 | 품질 gate에서 publish 차단 |

이 분류 기준을 적용하면서, 스크립트마다 달랐던 성공/실패 판단 기준이 하나로 통일됐습니다. 이후 백필이나 재처리를 수행할 때도 정말 다시 호출해야 하는 대상만 정확히 골라낼 수 있게 되었습니다.

## 3. Task 단위 세분화

### 3-1. 비대한 Task 단위 처리

초기에는 약 70여개의 전체 직업의 데이터를 최신화하는 작업을 하나의 Airflow Task로 구성했습니다.

이 구조에서는 마지막 직업을 처리하던 중 오류가 발생해도 Task 전체가 실패했습니다. 이후 재실행하면 이미 성공한 직업까지 처음부터 다시 처리해야 했고, 실제 실패 지점이 어디인지 확인하려면 전체 Task 로그를 직접 추적해야 했습니다.

특히 외부 API 호출과 대량 DB 집계가 하나의 큰 작업 단위에 묶여 있어, 실패 원인에 따라 필요한 부분만 재처리하기 어려웠습니다.

### 3-2. Dynamic Task Mapping

이를 해결하기 위해 전체 직업을 하나의 Task로 처리하지 않고, DB에서 조회한 직업·전직 목록을 기준으로 Airflow Dynamic Task Mapping을 적용했습니다.

각 mapped task는 하나의 직업·전직 범위를 담당합니다.

```text
build_job_stats_targets
        ↓
직업 A mapped task ─┐
직업 B mapped task ─┤
직업 C mapped task ─┤
       ...         ├─ 최대 24개 동시 실행
직업 N mapped task ─┘
```

이제 특정 직업에서 오류가 발생하더라도 전체 집계를 다시 실행하지 않고, 실패한 직업 task instance만 재처리할 수 있습니다. 이미 성공한 직업은 그대로 유지되므로 재처리 범위와 소요 시간을 줄이고, Airflow UI에서도 어느 직업에서 실패했는지 바로 확인할 수 있게 되었습니다.

다만 이 단계의 분할 단위는 직업 단위입니다. 하나의 직업 task 내부에서 장비, 스킬 등이 순차적으로 처리되므로 내부 세부 단계까지 독립적으로 재개하는 구조는 별도의 고도화 영역으로 남겨두었습니다.

### 3-3. 동시성 제한

mapped task를 무제한으로 실행하면 DB 집계 부하가 증가하고, 일부 worker에서 수행하는 API 호출도 외부 API rate limit에 영향을 줄 수 있습니다.

따라서 DAG 전체의 동시 실행 task 수를 제한했습니다. 외부 API를 직접 대량 호출하는 캐릭터 원천 동기화 경로에는 별도로 API concurrency, retry, backoff, rate limit 정책을 적용했습니다.

이처럼 작업 단위는 실패 지점을 좁힐 수 있을 만큼 작게 나누고, 동시 실행 수는 DB와 외부 API가 감당할 수 있는 범위 안에서 제한했습니다.

## 4. 재시도 로직

응답 분류를 표준화한 뒤에도, `retryable_error`로 분류된 대상을 어떻게 다시 처리할지는 별개의 문제였습니다. 429(rate limit)나 5xx, 일시적 네트워크 오류처럼 단순 재시도로 해결되는 오류와, 다음 DAG 실행까지 기다렸다가 별도로 재처리해야 하는 오류를 구분하지 않으면 두 가지 문제가 생겼습니다.

- 매 요청마다 즉시 재시도만 반복하면, 근본적으로 실패한 대상(예: 캐릭터가 삭제된 경우)까지 계속 재요청하게 됨
- 반대로 즉시 재시도 없이 전부 다음 배치로 넘기면, 일시적 오류 하나 때문에 불필요하게 재처리 주기를 기다려야 함

이를 두 단계로 나눠 처리했습니다.

1. **요청 단위 재시도**: API 요청 자체에서 최대 3회 재시도하고, 재시도 간 backoff를 적용합니다. 429나 일시적 네트워크 오류처럼 짧은 대기 후 재요청으로 해결되는 경우는 이 단계에서 대부분 흡수됩니다.
2. **Stage 기반 재처리**: 요청 단위 재시도 이후에도 `retryable_error`가 남으면, 즉시 재시도하지 않고 stage 테이블에 대상 식별자, 오류 분류, 원천 오류 코드, 오류 메시지를 저장합니다. 재처리 경로는 다음 실행 시 전체 대상을 다시 긁는 대신, stage에 남아있는 재처리 가능 대상만 선택해 처리합니다.

Airflow task 자체에도 재시도와 retry delay를 두었지만, 이는 DAG 실행 자체의 장애를 복구하기 위한 장치입니다. 개별 API 대상의 재처리는 stage 상태와 오류 분류를 기준으로 별도로 수행되므로, "DAG 전체를 다시 실행하는 것"과 "실패한 개별 대상만 재처리하는 것"이 서로 분리되어 있습니다.

이렇게 재시도를 요청 단위와 stage 단위로 나누면서, 일시적 오류는 빠르게 흡수하고 영구적이거나 반복되는 오류만 재처리 대상으로 선별할 수 있게 되었습니다.

## 5. 데이터 멱등성

데이터 파이프라인을 돌리면서 에러가 발생하는 경우, 데이터가 일부만 들어오거나 누락되는 문제가 발생할 수 있습니다.

던통 데이터 파이프라인에서는 대용량 데이터를 오류없이 처리하기 위해서 청크 단위로 커밋을 하다 에러가 발생하는 경우가 종종 발생했습니다. 이 때, 일부 데이터만 들어오는 문제가 발생했고, backfill 스크립트 실행 또는 task를 재실행 시켰을 때 기존에 있던 데이터와 중복되는 문제가 발생했습니다.

초기에는 멱등키 없이 단순 backfill과 task 재실행으로 진행을 했기 때문에 데이터 수가 누적되어 중복 데이터 또는 부분 데이터가 발생했고, 심한 경우 하루치 데이터가 거의 통째로 중복 적재되는 상황까지 있었습니다. 이를 처리하기 위해 DW, DM에 중복 데이터를 수동으로 처리하는 쿼리를 날려 해결했습니다. 더 나아가, 운영중인 App DB에 쿼리를 날려서 데이터를 제어하는 상황도 마주했습니다. 이러한 방식은 운영중인 DB에 크리티컬한 문제를 발생시킬 수 있고, 데이터 추적이 어려워지는 리스크가 발생할 수 있습니다.

이를 해결하기 위해 (date + job_id)를 멱등키로 도입했습니다. 하지만 이 구조에서는 task를 재실행할 때 해당 직업에 대한 모든 집계가 통째로 다시 처리되는 문제가 있었습니다. 기존 파이프라인 자체가 task 단위로 분리되어 있지 않았기 때문에, 재실행 범위가 항상 날짜+직업 전체로 퍼지는 구조였고, 이미 정상적으로 끝난 집계까지 불필요하게 재작업되는 비효율이 발생했습니다.

이를 다시 개선하여 멱등키에 task_type을 추가해 (date + job_id + task_type) 단위로 세분화하고, 기존 Task를 아래와 같은 방식으로 수정했습니다.

```text
┌─────────────────────────────┐
│   build_job_stats_targets    │
└───────────────┬──────────────┘
                │
                ▼
┌─────────────────────────────────────────────┐
│  Dynamic Task Mapping (최대 24개 동시 실행)   │
│                                              │
│  ┌───────────────┐                           │
│  │ 직업 A mapped task │                       │
│  └───────────────┘                           │
│        ...                                    │
│  ┌───────────────┐                           │
│  │ 직업 N mapped task │                       │
│  └───────────────┘                           │
└───────────────┬───────────────────────────────┘
                │  각 task는 (date + job_id + task_type) 멱등키로
                │  MERGE/UPSERT 수행
                ▼
        ┌───────────────┐
        │   DW / DM     │
        └───────────────┘
```

Dynamic Task Mapping을 도입해 집계 종류별로 분리했고, 각 task_type는 멱등키를 기준으로 MERGE/UPSERT를 수행하도록 구성했습니다. 결과적으로 특정 집계에서 에러가 발생해도 다른 집계에는 영향이 없었고, 재실행 시에도 문제가 발생한 task만 정확히 재처리할 수 있게 되었습니다.

기존에는 새로운 집계를 추가할 때 개발 환경에서 실패 리스크를 확인하지 못한 경우 에러를 처리할 때 추적 범위가 굉장히 넓었습니다. 멱등키를 세분화한 이후에는 에러 발생 시 추적 범위가 명확해졌고, 문제를 빠르게 해결할 수 있었습니다.

## 6. 데이터 정합성

데이터 정합성은 원본 데이터와 집계 결과가 서로 다른 의미로 해석되거나, 집계 기준이 통일되지 않아 결과가 달라지는 문제를 말합니다. 저희 파이프라인에서는 다음과 같은 정합성 문제 및 검증 장치를 다뤘습니다.

### 6-1. 집계 기준 불일치

집계 태스크마다 기준이 명확히 정의되지 않아, 같은 모수를 대상으로 함에도 태스크별로 집계 인원수가 달라지는 문제가 있었습니다.

같은 컨텐츠 클리어를 집계 하면서도, 특정 컨텐츠마다 null, 0을 다루는 방식이 달랐어서 모수가 달라지는 문제가 발생했습니다. 이를 해결하기 위해, 분석 대상을 먼저 정한 뒤, 특정 항목 데이터가 없는 경우는 집계 결과를 노출하는 시점에 null 또는 기타로 분류하는 방식으로 기준을 통일했습니다.

### 6-2. 시점 차이로 인한 불일치

현재는 매일 오전 06시 또는, 점검이 있는 목요일 10시에 데이터를 fetch하는 작업을 진행하고 있습니다. 하지만, 매일 1천만건이 넘는 데이터를 fetch하는 과정에서 처음에 fetch한 데이터와 끝에 fetch하는 데이터의 시간 차이가 유의미하게 발생하여 데이터가 오염될 수 있는 문제가 있었습니다.

일자 초기화 이전 또는 점검 이전으로 작업을 옮기는 경우 데이터를 특정 패치 시점 이전의 데이터로 맞출 수 있다는 장점이 있습니다. 하지만, task 시간이 일정하지 않아 기존 task 소요 시간 통계를 보고 수동으로 시간을 지정해줘야 합니다. 또한, 이렇게 시간을 지정해준다 하더라도 파이프라인 장애가 발생하는 최악의 경우 일자 초기화 또는 점검 이후로 데이터가 밀리는 문제가 발생합니다.

따라서, 매일 오전 데이터가 초기화된 이후에 데이터를 수집하는 방식으로 개선을 선택했습니다. 하나의 단점이 있다면, 대규모 패치가 진행된 경우 패치 이후에 플레이를 한 데이터와 그렇지 않는 데이터가 하루동안 섞이는 문제가 발생할 수 있습니다. 이는 서비스를 고도화하면서 해결해야 할 문제점이라고 생각하고, 현재는 개선 과제로 정리했습니다.

### 6-3. 집계 전후 검증

BigQuery와 같은 분산 OLAP 환경은 OLTP처럼 강한 트랜잭션 보장이 되지 않습니다. 따라서, 분산 환경에서 발생한 장애 등으로 일부 데이터가 누락된 채 집계가 완료될 가능성이 있습니다. 이러한 일을 실제로 겪지는 않았지만, 이러한 분산 처리 특성을 인지하고 사전에 방지하기 위해 원본 건수와 집계 결과 건수를 비교하는 검증 로직을 추가하여, 데이터 누락을 조기에 감지할 수 있도록 했습니다.

예를 들어, Table A에서 집계하여 Serving Table B로 데이터를 업데이트하는 과정에서, Table A의 원본 건수와 Serving Table B의 집계 결과 건수를 비교하여 데이터 누락 여부를 확인합니다.
Table A는 PostgreSQL을 사용하는 App DB일 수도 있지만, BigQuery를 사용하는 데이터 웨어하우스일 수도 있습니다. 후자의 경우는 앞서 말한 문제가 발생할 수 있기 때문에, 원본 건수와 집계 결과 건수를 비교하는 검증 로직을 추가하여 데이터 누락을 조기에 감지할 수 있도록 했습니다.

### 6-4. 이상치 탐지

집계 로직을 수정하는 과정에서 리텐션 집계 로직에 오류가 있었고, 이로 인해 리텐션 변화율이 1% 전후로 유지되던 수치가 하루 만에 10% 이상 급감하는 문제가 발생했습니다. 이를 사전에 감지할 수 있는 이상 탐지 로직이 없었기 때문에, 잘못된 수치가 그대로 프로덕션에 노출되었고 수동으로 확인한 뒤에야 문제를 인지할 수 있었습니다. 이 문제는 아직 해결하지 못했으며, 현재는 수동으로 지표를 점검하고 있습니다. 해결하지 못한 이유는 다음과 같습니다.

* 전일 대비 변동이 큰 경우 대규모 패치, 시즌 변경 등 정상적인 변동의 탐지의 어려움
* 데이터 부족으로 인한 요일, 계절성 대비 이상 탐지의 어려움

위 리텐션 급감처럼 "감소"는 로직 오류일 가능성이 높지만, 아래 DAU 사례처럼 "급증"은 정상적인 이벤트(신규 캐릭터 출시)일 수 있어 방향성만으로는 이상치 여부를 판단하기 어려웠습니다.

<img src="/images/posts/projects/duntong/duntong-DAU.jpeg" alt="던통 DAU" width="360" />

위 그래프에서 6월 초에 신규 캐릭터가 출시됐을 때 DAU가 5일 동안 74.0K, 83.3K 99.3K, 102.1K, 103.3K로 변화했습니다. 이러한 변화는 기존 우하향 하던 데이터와는 달랐습니다. 이렇듯, 신규 캐릭터 출시와 같은 대규모 패치에서 정상적인 변동 탐지의 기준을 어떻게 정할 것이냐가 문제였습니다. 변동 폭과 변동 기간 모두 정하기 어려웠고 기존에 관련 데이터를 가지고 있지 않았기 때문에 해결하지 못했습니다.

따라서, 이상 데이터가 발생하는 경우 이상 데이터를 어떻게 다룰 것인지가 아닌 데이터가 이상 데이터가 맞는지를 확인하는 절차를 강화했습니다. 해당 날짜에 해당하는 데이터가 올바른 데이터인지 이벤트 수를 체크하거나, 앞선 집계 전후 검증을 통해서 해당 데이터가 정상적인지 확인했습니다.

문제는 근본적으로는 해결하지 못했지만, 이상 데이터를 발견했을 때 빠르게 대응할 수 있도록 하는 것이 중요하다는 것을 배웠습니다. 위와 같이 대규모 업데이트와 같은 예상되는 문제가 있다면, 관련 데이터를 새로운 대시보드로 구축하여 모니터링 시스템을 강화하는 방식으로 문제를 해결할 수 있다고 생각합니다.

## 7. 회고

이전에는 Airflow 코드를 작성여여 파이프라인을 구축하는 것 부터가 어려움이었다면, 요즘에는 AI를 통해서 쉽게 코드를 작성할 수 있었습니다. 이 때문에 파이프라인 자체는 쉽게 구축할 수 있었지만, 코드 작성과는 별개로 Airflow를 운용하면서 발생하는 문제는 AI가 해결해주지 못했습니다.

데이터의 멱등성을 고려하지 못해서 중복 데이터를 제거하지 못하는 것, 정합성을 고려하지 못해서 오염된 데이터가 프로덕션에 들어가는 경우 등 데이터 파이프라인을 구축하면서 여러 가지 오류를 겪다보니 데이터를 일관성있고 확장성있게 처리하기 위한 방안들에 대해서 생각할 수 있었습니다. 또한, 가지고 있는 데이터의 퀄리티에 대해서도 생각해보는 계기가 되었습니다. 단순히 일회성으로 수집하고 버리는 것이 아니라, 가지고 있는 데이터를 계속 사용할 수 있는 환경을 구축하는 것이 중요하다고 생각했습니다.
